## Задача

Сделать собственный международный каталог коллекции компьютерных мышей и другого ретро-железа. Основное содержимое — мыши; в будущем возможны другие устройства. Сейчас коллекция опубликована на чужой русскоязычной площадке: https://collectionerus.ru/collections/old-mice/. Нужен независимый сайт, на который удобно ссылаться зарубежным коллекционерам и на форумах.

Исходные требования пользователя:

- Фотографии экспонатов в сетке, фильтры и поиск, переход по клику в отдельную карточку.
- Международная аудитория: английская версия обязательна; в прототипе есть EN по умолчанию и RU.
- Фотографии, миниатюры и текстовые поля; без постоянно работающего бэкенда и базы данных.
- Исходники желательно хранить в GitHub, сайт публиковать через GitHub Pages.
- Сохранить понятную организацию исходного каталога, но получить собственное оформление и домен.

В workflow при изменении ветки `main` GitHub Actions получает репозиторий на временной Linux-машине, настраивает Python 3.12, запускает генератор и проверку, затем публикует `dist` через Pages. Ручной запуск workflow также предусмотрен. Реальный базовый адрес для SEO берётся из `actions/configure-pages`.

## Как открыть и проверить

Для первого просмотра достаточно открыть `dist/index.html` в браузере. Более надёжный вариант — локальный HTTP-сервер. Из корня распакованной папки `mouse-archive`:

```bash
python3 scripts/build.py
python3 scripts/check.py
python3 -m http.server 8000 --directory dist
```

Открыть http://localhost:8000/. Для остановки сервера — Ctrl+C. Нужен Python 3.11 или новее; сторонние Python-пакеты для сборки не нужны.

Если Node.js установлен, синтаксис клиентского скрипта можно проверить отдельно:

```bash
node --check assets/app.js
```

Node.js не требуется для сборки или работы сайта.

Локальная сборка без SITE_URL намеренно не подставляет вымышленный публичный домен. После размещения на GitHub Pages переменная задаётся автоматически workflow. На локальном просмотре кнопки ссылок копируют локальные адреса; отправлять их собеседникам можно только после публикации.

## Фотографии и лимит GitHub Pages

Обсуждённое уточнение: ограничение 1 ГБ относится к опубликованному сайту, а не к изображениям, на которые он ссылается внешними URL. Рекомендации по размеру Git-репозитория — отдельная тема.

Допустимы два подхода:

- Сайт, данные и оптимизированные фотографии находятся в одном репозитории, пока объём позволяет.
- Сайт и миниатюры остаются в GitHub Pages, большие фотографии лежат во внешнем публичном хранилище. Браузер обращается к нему напрямую, бэкенд приложения не нужен.

Если сборщик скачивает внешние изображения в `dist`, они входят в размер публикации. Само хранение файлов в другой репе не помогает, если затем копировать их в сборку. Отдельный Pages-сайт для фотографий имеет собственные ограничения; raw-URL публичной репы возможны технически, но не утверждены в качестве основного фотохостинга.

Выбор провайдера внешнего хранения не сделан. В текущем коде внешние URL фотографий ещё НЕ поддержаны: генератор и проверка ожидают локальные пути. При реализации нужно отдельно обрабатывать http(s)-URL в проверке существования, построении относительных ссылок, галерее и Open Graph; сохранить поддержку локальных путей. Проверить все места использования images, не ограничиваться заменой одного поля. Закрытые файлы с истекающими подписанными ссылками не подходят в качестве постоянных публичных изображений.

## Следующие шаги

1. Открыть существующий прототип и уточнить правки дизайна у владельца. Не переписывать стек без необходимости.
2. Определить стабильную схему данных для полной коллекции: неизвестные даты, модель и конкретный экземпляр, категории устройств, признаки, ссылки на источники.
3. Решить, где будут храниться большие фотографии, и при необходимости добавить поддержку внешних URL. Обеспечить устойчивые адреса для ссылок и форумных вставок.
4. Сделать воспроизводимый импорт полного каталога: получить все записи и все фотографии, сохранить исходные ID и ссылки, проверять ошибки, исключить дубли. Не предполагать, что первая страница списка содержит всю коллекцию.
5. Перевести и редакционно проверить тексты и характеристики. Не придумывать отсутствующие сведения.
6. Заменить сообщения об образце на окончательные тексты только после полноценного переноса. Проверить контакты и публичность служебных данных.
7. Выбрать репозиторий и домен, включить GitHub Pages и проверить реальный workflow. Подключить HTTPS и проверить прямое открытие вложенных страниц, мобильную версию, SEO и ссылки для форумов.

## Критерии готовности

- Каталог и карточки доступны на EN/RU; карточка имеет постоянный прямой адрес.
- Все перенесённые фотографии отображаются без зависимости от исходной площадки, кроме явно оставленных ссылок на источники.
- Поиск, сочетания фильтров, сортировка, пустая выдача и переключение языка работают.
- На телефоне нет горизонтального переполнения страницы; галерея и фильтры доступны.
- После изменения данных публикация проходит через GitHub Actions без ручной сборки на компьютере.
- При внешнем хранении фотографии не копируются в `dist` без явной необходимости.
- Нет постоянного backend-приложения, обязательной БД или привязки к временному предпросмотру.

### Публикация без оригиналов фотографий

Пока оригиналы не публикуются: сборка исключает каталоги `originals` и `source-images`, карточки не содержат ссылок на них. Увеличенный просмотр использует WebP для просмотра. Исходники и метаданные оригиналов сохранены локально для последующего подключения внешнего хранилища.
