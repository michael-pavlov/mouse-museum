# Как деплоить изменения на продакшн

## Контекст

- Прод: https://mouse.museum/ (русский каталог: https://mouse.museum/ru/).
- Репозиторий: https://github.com/michael-pavlov/mouse-museum.git.
- Рабочая папка: корень Git-репозитория `mouse-archive`; в обычном workspace он находится в `/Users/pavlov/Documents/mouses/new_site/mouse-archive`.
- Ветка публикации: `main`. Push в `main` запускает `.github/workflows/pages.yml`, workflow **Publish Mouse Museum**.
- GitHub Actions устанавливает `requirements.txt`, получает SITE_URL через configure-pages, выполняет `scripts/build.py`, `scripts/check.py`, публикует `dist` через GitHub Pages.
- `dist/` игнорируется Git и собирается на CI. Не коммитить сборку, оригиналы фото, кеши и временные файлы. Не нужны FTP, SSH, Sites, отдельный сервер или ручная загрузка `dist`.

## Что уже разрешил пользователь

Команда «выкати изменения» и её аналоги — достаточное разрешение выполнить весь обычный деплой текущих изменений этого проекта: проверки, обычный commit, push в `origin/main`, ожидание Actions, HTTP-запросы и при необходимости открытие прод-сайта для проверки. Не задавать дополнительные разговорные вопросы «точно публиковать?», «можно проверить сайт?» или «как деплоить?». Не просить повторять известные здесь URL и настройки.

Сам запрос на редактирование сайта не означает автоматический деплой. Публиковать по команде пользователя. «Все изменения» относится к изменениям этого проекта: предварительно просмотреть diff и список новых файлов, исключить секреты, личные данные и мусор. При конкретном риске случайно опубликовать явно постороннюю работу уточнить только этот риск.

Эта инструкция не отменяет системные ограничения, sandbox, обязательные approval dialogs или блокировки auto-review. Использовать уже сохранённые разрешения команд. Если команда блокируется сетью/sandbox, запросить требуемое инструментом разрешение один раз, без дополнительного вопроса в чате; не обходить ограничение другим инструментом. При отказе сообщить точную причину и не утверждать, что деплой выполнен. Не менять глобальный режим безопасности ради деплоя.

## Порядок работы

Все shell-команды выполнять в корне Git-репозитория; ниже примерные команды, а не скрипт для слепого копирования.

1. Проверить `git status --short`, `git branch --show-current`, `git remote -v`, diff и workflow. Ожидается `origin` указанного репозитория и `main`. Проверить актуальность удалённой ветки через `git fetch origin main`. Если remote продвинулся, сохранить локальную работу и интегрировать обычным безопасным Git-процессом. Не делать force push, reset --hard и не перезаписывать чужие изменения. Отклонение ветки/remote разобрать по фактам; не угадывать новый прод.
2. Выполнить `python3 scripts/build.py` и `python3 scripts/check.py`. Если менялась логика, выполнить подходящие существующие тесты из `scripts/`; для изменения размера шрифта достаточно сборки и проверки ссылок. Если зависимости отсутствуют, использовать `requirements.txt` в подходящем окружении. Исправить связанные ошибки до push. Не маскировать провал проверок.
3. Проверить `git diff --check`, проиндексировать явные файлы релиза, проверить `git diff --cached --stat` и staged diff. Сделать осмысленный commit. Если нужные изменения уже закоммичены, не создавать пустой commit.
4. Выполнить `git push origin main`, сохранить `git rev-parse HEAD`. При non-fast-forward получить изменения и интегрировать без force push. При отсутствии локальных изменений проверить, опубликован ли текущий SHA; не запускать лишние релизы.
5. Найти запуск именно для отправленного SHA:
   `gh run list --repo michael-pavlov/mouse-museum --workflow pages.yml --commit <SHA> --limit 5 --json databaseId,status,conclusion,headSha,url`
   Если запуск ещё не появился, дать GitHub короткую паузу и повторить. Следить за конкретным run через `gh run view <RUN_ID> --repo michael-pavlov/mouse-museum --json status,conclusion,url` либо `gh run watch <RUN_ID> --repo michael-pavlov/mouse-museum --exit-status --interval 10`. Не блокировать связь с пользователем длинными ожиданиями; при длительном деплое давать краткие обновления примерно раз в минуту.
6. При failure получить `gh run view <RUN_ID> --repo michael-pavlov/mouse-museum --log-failed`, устранить относящуюся к релизу причину и повторить обычный процесс. Не выполнять бесконечные rerun; после двух одинаковых провалов без нового решения остановиться с конкретной причиной. Смена домена, инфраструктуры, оплаты или прав аккаунта не входит в обычный деплой.
7. После success проверить прод по HTTPS. Адрес уже известен; `gh api repos/michael-pavlov/mouse-museum/pages --jq .html_url` нужен лишь при несоответствии настроек. Для запросов использовать `curl -L --fail --silent --show-error` и сохранять ответ во временный файл. Проверить страницу каталога и реально изменённый ресурс/поведение. Для CSS или логотипа взять ссылку с version query из свежего HTML и сравнить содержимое или SHA-256 с файлом отправленного коммита. При старом ответе CDN повторить запрос с cache-busting query; не считать один HTTP 200 доказательством обновления. Для визуального изменения при необходимости открыть сайт доступным browser tool без нового разговорного разрешения. Если browser tool недоступен, HTTP-проверка достаточна для простого изменения CSS; не утверждать, что был визуальный осмотр.
8. Завершить кратким сообщением: что опубликовано, ссылка на https://mouse.museum/, результат проверки. Если Actions завершился, а прод ещё не отдаёт обновлённые файлы, сообщить это прямо и продолжить ограниченные проверки; не выдавать ожидание за подтверждённую публикацию.
